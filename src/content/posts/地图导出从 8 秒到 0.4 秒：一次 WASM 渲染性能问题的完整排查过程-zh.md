问题的表面现象其实很简单——地图导出 PNG 变慢了，而且慢得已经到了用户能明显感知的程度。

但真正麻烦的地方不在“慢”这个结论本身，而在于接下来该怎么推进。

日志里能看到很多看起来可疑的点：道路渲染慢、公园渲染慢、渐变也慢、PNG 编码也不便宜。

只要愿意动手，几乎每个地方都能找出一个“也许可以优化”的方向，尤其是在 Coding Agent 的加持下。

但如果一开始就冲进代码里改，很容易陷入另一种更糟糕的状态，瞎忙活：改了很多，却不知道到底是哪一步真正起作用，甚至改掉了画质，最后总导出时间也没真正回到可接受范围。

而且这次回归并不是凭空出现的，前一轮为了修正地图视觉规则，我刚把一部分原本放在前端数据层的几何关系处理，迁到了 WASM 渲染层里：例如 `parks` 不再覆盖 `water`，道路也可以在最终渲染时避开 `water + parks`。这条方向在架构上其实是对的，因为它让前端只负责传原始 `roads / water / parks`，把最终视觉规则交给真正负责输出图片的那一层去决定。

但它也带来了一个直接后果：一些原本不该出现在默认导出流程里的重处理路径，开始进入默认流程。

所以这篇文章的重点，不是展示我最后把哪几个函数改快了，而是完整展开这次性能优化是怎么一步步推进的：

- 我如何先把问题边界收紧
- 如何建立可重复的测试闭环
- 如何设计实验，判断哪些方向值得继续、哪些不值得做
- 为什么最终保留的是一套混合采样方案，而不是简单粗暴地把所有东西都拉到更高倍率

顺带一提，这次过程中我明显感觉到，一套借鉴 Matt Pocock 工作流思路的诊断方法，确实帮我少走了不少弯路。它的价值不在于“替我想出优化点”，而在于强迫整个过程始终围绕边界、证据和决策推进，而不是一头扎进实现细节里。

如果提前把最后的结果说清楚，那么这次优化其实可以概括成两步：

- 第一轮先把默认导出流程里那几个很重的分支移出去，让导出时间从失衡状态回到可控区间
- 第二轮不再追求统一更高倍率，而是收敛到 `Motorway + Primary = 2x`、其余维持 `1x` 的混合采样方案，在画质和总导出时间之间找到一个更值的平衡点。

## 1. 问题背景：一次“只是变慢了”的导出问题

这个问题发生在一个地图导出链路里。用户在前端选择地点、样式和导出参数后，数据会经过前端处理、worker 调用，再进入 WASM/Rust 渲染链路，最后编码成 PNG 下载。

用户真正感知到的不是某个内部阶段的耗时，而是点击导出之后，需要等多久才能拿到最终图片。

最开始给出的日志已经很长，而且信息量不小。前端预处理阶段其实并不夸张：地图数据读取、分片、worker 处理都在毫秒级到几十毫秒级范围内。但进入 Rust 渲染之后，几个阶段的时间突然被拉得很长，尤其是：

- `draw_parks`
- `draw_roads`
- `draw_gradients`
- `encode_png`

其中道路渲染甚至到了十秒级。这已经不是“某个地方有点慢”的程度，而是足以让整次导出体验明显变差。

但问题并没有因为日志里有几个大数字就变简单。恰恰相反，这类日志最容易制造一种错觉：只要挑一个最大的数字下手就行了。

可真实情况是，性能问题常常不是单点问题，而是由默认路径选择、采样倍率、图层策略、路径构建方式和最终编码成本共同叠加出来的。如果没有统一的判断标准，就很容易在一堆局部热点里来回摇摆。

这次一开始就有两个很明确的约束，也正是这两个约束决定了后面的整个优化方向。

- 第一，目标不是让某个局部基准测试变漂亮，而是让最终导出等待时间明显回落。也就是说，关注的是用户可感知的总等待时间，而不是某一个函数自顾自地快了多少毫秒

- 第二，不能为了这一点性能提升，明显伤害最终画质。如果优化带来的收益只有一点点，但肉眼可见地让地图变丑、边缘更差、主干道更糊，那这种优化在产品层面其实没有意义

这两个约束听起来很普通，但它们非常重要。因为一旦目标变成“体感级速度恢复”和“尽量不伤画质”，很多表面上能做的优化，其实就不值得优先推进了。后面整篇文章里的很多取舍，都是围绕这两个标准做出来的。

## 2. 先别急着优化：我先把问题边界收紧了

性能问题最常见的失败方式之一，就是一开始就动手改代码。看到日志里哪个数字大，就先去那个函数里翻一翻，看到某个阶段秒级，就先猜它一定是根因。这种做法偶尔会撞对，但大多数时候只会把问题越搅越乱。

因为一个完整的导出流程里，可能同时包含很多层次：

- React 事件与状态更新
- 前端数据准备
- worker 调用与数据传输
- WASM 入口与 Rust 数据解析
- Rust 渲染阶段
- PNG 编码
- 文件下载与浏览器落盘

如果这些层全都混在一起排查，最后的结果通常不是“更全面”，而是“更失控”。每个层面都能找到一些看起来值得研究的点，但这些点之间未必真的和当前问题最相关。

所以这次我先做的不是优化，而是收边界：这轮分析只关注 **WASM 收到输入之后的路径**。

更具体一点，纳入分析范围的是：

- WASM exported function 入口
- WASM 和 Rust 之间的绑定层
- Rust 内部的数据解析、转换、渲染准备
- 渲染阶段本身
- PNG 编码
- Rust 返回 PNG bytes 之前的内存路径

明确不分析的包括：

- React 事件处理
- 前端状态管理
- JS 调用 WASM 之前的数据准备
- 用户点击按钮后的 UI 流程
- Blob / objectURL / 下载触发
- 网络请求
- WASM 初始化加载

这一步的价值，远比它表面看起来的大。它不是为了让分析“更窄一点”这么简单，而是直接删掉了一大堆会让讨论发散的方向。

这样后面每一次新增日志、每一次提出假设、每一次比较数据，都是围绕同一个核心问题展开的：**既然前端前置处理不是主要矛盾，那 Rust/WASM 这一段到底发生了什么？**

这也是我在这次过程中，最明显感受到 Matt Pocock 风格工作流带来帮助的地方之一。它并没有替我找到答案，但它逼着整个过程先做一件非常工程化的事：

- 先把“问题是什么”说清楚
- 再开始分析“怎么解决”。

很多性能优化之所以最后越做越乱，不是因为工程师不会优化，而是因为一开始没有把问题缩成一个真正可处理的问题。

收边界之后，后面的工作才有了基础，接下来要做的，就不是“继续猜哪里慢”，而是建立一套可以反复跑、可以稳定比较、可以支撑后续决策的测试闭环。

## 3. 建立测试闭环：浏览器实测是主基准，本地回放是辅助

这次优化过程里，真正让我从“看到一堆慢点”走到“开始有把握地做判断”的，不是先改了哪段代码，而是先把测试闭环建立起来了。

很多性能问题之所以越做越乱，不是因为工程师不够努力，而是因为反馈循环太差。

每次都要重新走一遍完整流程，步骤多、变量多、环境还不稳定，最后只能得到一种很脆弱的感觉：似乎变快了，或者似乎没什么变化。只要反馈循环不稳定，后面的任何优化判断都会越来越依赖主观印象。

这次我很快意识到，至少要同时满足两件事：

- 要有一个**最终可信**的基准，用来判断用户真实会感受到什么
- 也要有一条**更便宜、更快**的辅助测试流程，用来支撑反复试验

### 3.1 为什么浏览器真实导出必须是主基准

最终用户体验发生在哪里，主基准就应该放在哪里。这个原则听起来很普通，但很多性能排查一开始就会在这里走偏。

在这个问题里，用户真正关心的是：点击导出之后，要等多久才能拿到最终 PNG。这个等待时间包括了真实分辨率、真实 worker 调用、真实 WASM 渲染、真实 PNG 编码，以及浏览器这一层的整体表现。所以后面无论我本地做多少回放、做多少脚本对比，最终判断仍然要回到浏览器导出链路来确认。

这意味着浏览器不是一个“顺便测一下”的环境，而是整个案例里的最高优先级证据源。它不是辅助，它才是最终裁判。

### 3.2 但为什么我又额外做了真实案例回放

如果只靠浏览器点一遍又一遍，测试也会很快变得低效。

原因很现实：

- 完整流程太长
- 每次都要重新走一遍前置步骤
- 不方便快速对比多个小改动
- 一些并不重要的外围因素也会混进来

所以我后面做了一件很关键的事：把一次真实导出中的中间输入保存下来，变成可以本地反复重放的测试样本。

具体保存的是几类已经处理好的数据：

- `roads-shards.json`
- `water-bin.json`
- `parks-bin.json`
- `config.json`

这样后面很多验证就不需要每次都重新点页面、重新抓数据、重新走完整前端准备链路，而是可以直接把这些中间输入喂给渲染核心去跑。

这件事的价值非常直接：它把一个“每次都要重走整条链路”的测试问题，变成了“可以反复播放同一个真实案例”的测试问题。

### 3.3 回放解决了什么，没解决什么

这一点我后来越来越明确：真实案例回放非常有用，但它不能替代浏览器。

它解决的是：

- 复现成本高
- 调试回合太慢
- 不方便针对核心渲染链路做高频试验
- 每次都要重复很多与当前问题无关的步骤

但它没有解决这些问题：

- 浏览器真实导出路径里的最终等待体验
- 浏览器环境下的完整导出时长
- 用户真正感知到的“导出到底还慢不慢”

换句话说，回放的角色不是“更高级的真相”，而是“更便宜的辅助测试流程”。它非常适合做快速重放、快速验证、快速比较，但最后的判断仍然必须回到浏览器主基准上。

这一步看起来像是在搭测试设施，但它实际上很大程度上决定了后面整轮优化的可信度。如果没有这套双层结构，后面的很多取舍都会变得很虚：本地好像更快了，但浏览器是不是也真的变好了？如果这个问题始终没法回答，那后面的优化就很容易沦为自我安慰。

### 3.4 这套闭环最后长什么样

![https://imgf.0v0.one/landscape/webp/20260623_062014_7106.webp](https://imgf.0v0.one/landscape/webp/20260623_062014_7106.webp)

这次性能优化最后形成的是一套双层测试闭环：浏览器真实导出始终是主基准，真实案例回放只负责缩短迭代回合，不能替代最终判断。具体流程大致是下面这样：

1. 用浏览器真实导出拿最终判断
2. 在需要更快迭代时，保存并回放真实案例的中间输入
3. 在 Rust/WASM 核心路径里补最小埋点
4. 用本地回放快速试某个方向
5. 再回到浏览器确认这个方向是否真的带来用户可感知收益

这套闭环最大的价值在于，它把“性能优化”从一种容易失控的试错行为，变成了一种有主基准、有辅助测试流程、有验证节奏的工程过程。

## 4. 日志不够，就补最小埋点，而不是先重构

测试闭环建立之后，下一个问题马上就来了：现有日志虽然已经能证明“确实很慢”，但还远远不够回答“到底慢在哪，先改哪里最值”。

这是性能问题里另一个很容易走偏的地方。很多时候工程师会在这里走向两个极端：

- 要么觉得日志已经够多了，继续靠猜
- 要么一口气到处加 log，加到最后自己都淹没在输出里

这次我有意避开了这两个极端。思路很简单：**只补那些能直接区分当前假设的最小观测点。**

### 4.1 原始日志回答不了什么问题

最开始那批日志虽然已经告诉我：

- `draw_roads` 很贵
- `draw_parks` 很贵
- `draw_gradients` 也不便宜
- `encode_png` 也有成本

但它仍然回答不了很多关键问题，例如：

- 慢在渲染本身，还是慢在最后编码？
- 道路渲染内部到底慢在路径构建、外描边，还是主线填充？
- 哪一类道路最贵？
- 当前问题是不是主要由像素规模放大导致的？
- 是某个局部路径特别差，还是整个渲染策略有系统性问题？

如果这些问题回答不了，后面的优化顺序就只能靠感觉。

### 4.2 后来补了哪些关键埋点

我最后补的不是一大堆分散日志，而是几组足够支持下一步决策的观测点。

| 类别          | 代表埋点                                                | 想回答的问题                                  |
| ------------- | ------------------------------------------------------- | --------------------------------------------- |
| roads 子阶段  | `build_road_paths` / `stroke_casing` / `stroke_fill`    | `draw_roads` 到底慢在 build、casing 还是 fill |
| roads 细分    | 各道路等级 breakdown                                    | 是哪类道路最值得保留高质量、哪类不值得        |
| encode 子阶段 | `downsample_rgba` / `png_encode`                        | 当前主矛盾在 render 还是 encode               |
| 像素规模代理  | `total_pixels` / `main_pixmap_bytes` / `raw_rgba_bytes` | 成本是不是主要被像素规模放大了                |

这几组信息一出来，问题就不再只是“总耗时很大”，而是开始变成几个可以分别决策的问题：道路内部先看哪一段，编码是否需要优先动，统一高倍率是不是在把所有阶段一起推贵。

### 4.3 为什么这叫最小埋点

这里的“最小”不是说埋点少，而是说：**每个埋点都必须有明确用途。**

比如，如果我要判断是不是道路阶段本身出了问题，那么把 `draw_roads` 拆成 `build_road_paths`、`stroke_casing`、`stroke_fill` 就非常有价值；但如果某个额外日志既不能帮助我排除假设，也不会影响下一步决策，那它就不该先加。

这其实是一种很重要的工程约束。埋点不是越多越好。越是复杂问题，越应该避免让观察手段本身变成新的噪声源。

### 4.4 诊断工作流在这里真正帮到的地方

如果没有前面那套诊断工作流，这一步很容易退化成一句很常见的话：

> 再多打点日志看看。

但真正有效的做法不是“再看看”，而是先回答两个问题：

- 当前最值得验证的假设是什么？
- 哪个观测点最能帮助我区分它是否成立？

所以这一步的真正变化，不是“我加了更多日志”，而是“我让日志和假设一一对应了”。

这使得后面的每一次对比，都不再只是看数字，而是在读一个有上下文的证据系统。

## 5. 第一轮高收益恢复：先把默认导出流程里那几个很重的分支移走

当测试闭环和关键埋点都建立起来之后，第一轮真正有价值的优化方向很快就浮出来了：默认导出流程里有几个非常重的分支，本身就不应该一直处在默认开启状态。

这里最典型的就是两条 mask 相关路径：

- park / water overlap 的处理
- road / terrain mask 的处理

### 5.1 为什么我最先盯上了这两条路径

一开始看日志的时候，`draw_parks` 和 `draw_roads` 的时间就已经很夸张。但只看总时间还不够，必须把它和代码路径对应起来。

结合后来看到的实现，这两条路径之所以危险，不只是因为它们慢，而是因为它们属于一种很典型的“默认导出时每次都会踩到的重分支”：

- 为了做更精细的视觉处理，额外创建整层图层
- 重建完整路径
- 执行额外的 clear / composite / masking
- 让本来已经昂贵的绘制阶段再叠一层成本

这类逻辑的问题，不是“局部实现还可以再抠一点”，而是它们一旦默认开启，就会让所有默认导出一起付出成本。

### 5.2 为什么这一步优先级最高

很多性能问题里，最值钱的不是抠一个局部 5% 或 10%，而是先把一个不该放在默认路径里的重分支移开。

这一步之所以优先级高，有几个原因：

- 它影响的是默认路径，不是边缘场景
- 它带来的收益是全局性的
- 它不要求我先把每个底层实现都优化到极致
- 它能很快验证“是不是这条策略本身就放错位置了”

从工程判断上说，这种方向往往比继续在昂贵路径内部精修更划算。

### 5.3 最终做法：不是删除能力，而是不再让它默认出现在导出流程里

这里很重要的一点是，我并没有把这些视觉处理逻辑直接删掉。

最终做法是：

- 保留功能
- 保留开关
- 但把它们移出默认导出流程
- 只有用户明确开启时，才走那条更重的渲染逻辑

这个决策背后的思路很实际：如果一条视觉增强路径确实更贵，那就应该让它以“显式成本”的方式存在，而不是让所有用户默认买单。

### 5.4 这一轮带来的效果

这里有一点要先说清楚：下面这组变化更接近一次**把默认导出流程改回合理状态**，或者说一次**回归恢复**，而不是通常意义上的普通局部优化。前一个状态下，parks 阶段默认会走进更重的 park / water mask 路径；后一个状态下，并不是 parks 填充算法本身被优化了几十倍，而是这套高成本的额外处理不再出现在默认导出流程里，默认导出重新回到了更合理的直接绘制方式。

也因为这个原因，我这里只保留一条能被原始日志前后对比、且能比较干净说明“默认不再走那条高成本处理路径”之后发生了什么的数据。像 `draw_roads` 和 `render total` 这类指标，后续又叠加了第二轮道路优化，如果这时硬把它们也写成同一轮因果表，反而会把证据弄脏。

这一步做完之后，默认导出路径里的异常成本先被压下去了一大块。尤其是 `draw_parks`，从原本的秒级夸张耗时，直接回到了更接近单次多边形填充的量级。

这还不是问题的终点，因为 roads 仍然很贵。但至少第一轮恢复已经先把默认路径从明显失衡的状态里拉了回来，让后面的优化不再建立在一个坏掉的基线上。

| 指标         |     变更前 |    变更后 |   变化 | 说明                                                         |
| ------------ | ---------: | --------: | -----: | ------------------------------------------------------------ |
| `draw_parks` | 8795.30 ms | 410.70 ms | -95.3% | 按前后日志对比约下降 95%，但这更接近一次把默认导出流程改回合理状态：前一状态默认会走入更重的 park / water mask 路径，后一状态恢复为更合理的默认直接绘制方式 |

![https://imgf.0v0.one/landscape/webp/20260623_062014_1461.webp](https://imgf.0v0.one/landscape/webp/20260623_062014_1461.webp)

### 5.5 这一轮最值得复用的经验

如果要把这一节压缩成一句最有价值的经验，那就是：

> 先处理默认导出流程里那些很重的分支，往往比抠局部小优化更值。

这不是说局部优化不重要，而是说，在一个已经明显退化的系统里，先把策略层面的高成本默认选择纠正过来，通常能最快恢复整体健康度。

而这一步一旦做对，系统只是从“失衡”回到了“可控”，还没有到“最优”。后面的道路优化、采样实验和质量取舍，才真正开始建立在一个值得继续往下推的基线上。

## 6. 问题还没结束：道路依然是最大热点，于是我开始设计实验

把默认导出流程里那些很重的分支移走之后，情况明显好了一些，但问题并没有真正结束。日志里最显眼的那个大头，仍然是道路渲染。

这时候最危险的做法，其实是继续沿着“哪个数字最大就改哪个”的思路往下冲。比如看到某个道路等级慢，就直接去削它；看到 fill 比 casing 贵，就直接盯着 fill 下手。这些方向未必完全错，但如果没有更清晰的实验框架，它们很容易把优化重新拉回局部小修小补模式：每次改一点、测一点、解释一点，但始终缺少一个更系统的比较方法。

### 6.1 为什么 roads 成了第二阶段的核心问题

在第一轮恢复之后，公园、mask 相关路径的异常成本已经被明显压下去了，默认路径不再失衡；但 `draw_roads` 仍然长期占据总时间的大头。后来补出来的分阶段日志进一步说明了这个问题：

- `build_road_paths` 不是主矛盾
- 真正昂贵的是 `stroke_casing` 和 `stroke_fill`
- 而且不同道路等级之间的耗时也并不均匀

| 道路阶段           |        耗时 | 说明                                   |
| ------------------ | ----------: | -------------------------------------- |
| `draw_roads total` | 10000.88 ms | 优化后日志里的道路总耗时，仍然是主热点 |
| `build_road_paths` |    88.70 ms | 路径构建本身不是主要瓶颈               |
| `stroke_casing`    |  4026.20 ms | 外描边成本很高                         |
| `stroke_fill`      |  5885.30 ms | 主线描边成本更高                       |

这意味着问题已经从“是不是某条重分支放错位置”进入了另一个层面：**当前整套路径在不同采样倍率、不同道路等级下，到底值不值得维持现状。**

### 6.2 为什么这时候不能继续拍脑袋

如果只是局部看 roads 的 breakdown，很容易产生很多看似合理的优化冲动：

- 更激进地简化低等级道路
- 继续削掉更多 casing
- 调整 stroke 参数
- 统一降低采样倍率
- 甚至直接把采样倍率全部降掉

问题在于，这些方向不是没有道理，而是它们彼此之间很难只靠直觉比较。比如：

- 降倍率确实会快，但画质损失有多明显？
- 低等级道路继续简化，真的能换来用户感知上的收益吗？
- 保留主干道高质量、牺牲次要元素，是否是一种更合理的折中？

这些问题如果继续靠讨论，很快就会陷入“我觉得”和“看起来像”。所以我后来明确做了一个转向：**不继续盲猜，而是把这个问题改写成实验问题。**

### 6.3 从优化争论切到实验设计

一旦把问题改写成实验问题，后面的结构就清晰了很多。我要回答的不再是：

- 采样倍率到底应该是多少

而是：

- 全 1x 会发生什么
- 全 2x 会发生什么
- 如果只给最重要的部分保留更高采样，其余维持 1x，会发生什么

这个转变非常关键。因为它让后面的工作从“某种更聪明的猜测”变成“设计几个最有信息量的对照组”。而一旦进入对照组思维，讨论就开始围绕基线、变量和比较条件展开，而不是围绕各自偏好的优化直觉展开。

### 6.4 为什么实验设计比继续微调更重要

很多性能优化最耗时间的地方，不是实现本身，而是工程师花了大量时间在错误方向上做精细优化。一个没有实验框架的团队，最容易做出的事情就是：在一堆都“有点道理”的方向里来回试，最后积累了很多零散改动，却没有形成稳定结论。

这次我后面之所以能比较快地收敛，不是因为一开始就知道混合采样一定是答案，而是因为我把优化问题先整理成了一个更容易比较的问题：

- 哪些配置值得进实验
- 哪些配置只是在增加测试噪音
- 哪些对照最能改变当前判断

这一步实际上就是后面整组采样实验的起点。

## 7. 从统一超采样到按元素分配预算

如果只看表面，采样倍率看起来像一个很简单的旋钮：把它从 1 调到 2，画质会更好，成本也会更高；继续往上调到 3，理论上画质会继续提升，代价也继续增加。很多系统一开始都是按这种统一倍率思路设计的，因为它足够直观，也足够省事。

但这次对 roads 的第二轮分析，慢慢让我意识到：**统一倍率思路虽然简单，却不一定是最值钱的思路。**

### 7.1 为什么统一 `all_2x` 一开始看起来很合理

从直觉上说，统一 `all_2x` 有几个天然优势：

- 配置简单
- 语义清晰
- 不需要区分各类元素
- 整体视觉也更一致

如果问题只是“能不能让边缘更平滑”，那这样的处理方式非常自然。也正因为如此，一开始把它当成基线去比较，是完全合理的。

### 7.2 但它真正的问题是什么

继续看日志之后，一个问题越来越明显：不是所有元素都同样值得更高倍率。

有些元素在 2x 下确实更好看，也更接近“值回票价”；但另一些元素即便吃了更高倍率带来的成本，视觉收益却非常有限。更麻烦的是，这些成本并不是平均分布的，而是会集中出现在某些阶段、某些图层、某些元素类别上。

也就是说，统一提高倍率的本质不是“把所有地方都合理地提升一点”，而更像是“让所有地方无差别地一起涨成本”。一旦问题开始从总成本角度看，这种无差别提升就显得越来越不划算。

### 7.3 把倍率问题改写成配置问题

后面真正改变局面的，是把统一倍率思路拆成了一个更细粒度的配置问题，也就是后来形成的 `render_scale_config`。

它不再只允许回答：

- 当前是 1x 还是 2x

而是允许回答：

- 背景要不要 2x
- 水体要不要 2x
- 公园要不要 2x
- 哪些道路等级要 2x
- 渐变要不要 2x
- 文字要不要 2x

这一步一开始看起来像是在增加复杂度，但本质上是在把一个粗糙的全局开关，变成一个可以实验、可以比较、可以做取舍的预算分配面板。

### 7.4 为什么这是更好的优化视角

一旦问题被改写成配置问题，超采样就不再是一个“统一更高是不是更好”的问题，而变成了一个更工程化的问题：

> 如果高倍率是一种昂贵预算，哪些元素最值得拿到这份预算？

这个视角变化非常重要。因为它自动把“值不值”带进了讨论。

- 如果某个元素在 2x 下很贵，但肉眼收益很小，那它就不该优先拿预算
- 如果某个元素虽然贵，但它恰好处在用户最能看出的地方，那它就更有资格保留高倍率

从这一刻开始，优化问题就不再是“把采样倍率调到多少”，而是“把有限成本预算分配给谁”。

### 7.5 `render_scale_config` 真正解决的不是 API，而是实验可控性

这里还有一个容易忽略的点：这个配置对象的价值，不只是未来可以继续细调，而是它让实验从此变得可控。

因为一旦有了按元素、按道路等级拆开的配置，后面做对照时就可以更清楚地知道：

- 当前到底变了哪些维度
- 哪些维度保持不动
- 这轮实验真正想验证的是什么

也就是说，它不只是一个更复杂的参数结构，而是一个让后续实验矩阵可以被设计出来的基础设施。

## 8. 浏览器实测告诉我的：更高倍率并不自动等于更高价值

有了 `render_scale_config` 之后，真正重要的工作反而不是立刻决定“默认就该怎么配”，而是回到浏览器里做几组最有信息量的实测对照。

这也是我后面一直坚持的一个原则：本地回放可以帮助我缩短迭代回合，但最终值不值、用户会不会感知到、画质损失大不大，这些判断还是要回到浏览器导出链路上看。

### 8.1 我重点比较了哪些组合

为了避免实验面失控，第一轮并没有把所有细粒度组合都测一遍，而是先抓几个最有信息量的场景：

- `all_1x`
- `all_2x`
- `Motorway + Primary = 2x，其余 = 1x`

同时还把导出分辨率和超采样分开看，分别记录导出 1x 和导出 2x 下的表现。这一点后来证明非常重要，因为导出分辨率和内部采样倍率是乘法关系，如果不拆开看，很容易把两个成本源混在一起。

### 8.2 从这些结果里，我真正看到了什么

浏览器实测最有价值的一点，不是给出了一堆数字，而是让我看到不同阶段对倍率的敏感度其实非常不一样。

有些阶段随着倍率上升，成本会很明显地放大；但另一些阶段虽然也变贵了，视觉收益却没有同步增长。换句话说，倍率带来的成本增长和视觉收益增长，并不是同一条曲线。

这比“2x 比 1x 更贵”这样的常识更重要。因为常识谁都知道，真正困难的是：**更贵的部分，到底是不是更值。**

更具体一点，这轮浏览器对比最后给我的判断大致有两条。第一，`all_1x` 确实是最低成本基线，但主干道边缘质量下降最明显，尤其在用户更容易注意到的 `motorway / primary` 上更容易看出差异。第二，`all_2x` 虽然整体更整齐，但它把几乎所有阶段都一起推贵了，最终换回来的视觉收益并没有等比例增加；和混合采样相比，它更像是在为“不那么关键的元素”也支付同样高的成本。

### 8.3 一个重要的直觉变化：不是更高倍率就更值得

后面甚至还讨论过 `all_3x`。理论上讲，倍率继续上升当然会进一步提高内部像素工作量，但从浏览器实测看，到了这个阶段，很多收益已经开始进入边际递减区。

也就是说，成本还在涨，但肉眼能稳定感受到的提升已经没有那么明显了。

这个判断非常关键，因为它直接阻止了后面的一个常见误区：既然 2x 有帮助，那 3x 会不会更好？

答案不是绝对不会，而是：**在这个案例里，它没有表现出足够高的价值。**

一旦把问题从“理论上更高会不会更好”重新拉回“用户是否真的能感知到更多收益”，后面的很多选择都会自然收敛下来。

### 8.4 为什么这里不能只看局部热点

还有一个很重要的认识变化是：不能只因为某个阶段对倍率敏感，就直接把它当成最值得保留高倍率的对象。

因为性能决策最终不是“谁变化最大”，而是：

- 这个变化是不是用户真正关心的
- 它换来的视觉收益是不是足够明显
- 它会不会把总等待时间重新拖回不可接受区间

浏览器实测的价值就在这里。它把问题从一堆局部数字重新拉回了最终体验。

## 9. 最终取舍：为什么我保留了 Motorway + Primary 2x，而不是 all_2x

当几组关键对照都跑完之后，问题其实就不再是“哪组数据更漂亮”，而是一次很典型的工程取舍：到底哪一种配置在当前约束下最值得被保留下来。

### 9.1 候选方案并不复杂，但取舍标准必须清楚

这次真正进入最后比较的，核心就是三类方案：

- `all_1x`
- `all_2x`
- `Motorway + Primary = 2x，其余 = 1x`

如果只从“速度”看，`all_1x` 自然最轻；如果只从“统一画质”看，`all_2x` 也很有吸引力。但问题从来不是单维度的。

这里真正关键的是，判断标准必须保持一致：

- 总导出时间是否有明显改善
- 用户是否能感知到这种改善
- 视觉质量是否出现明显退化
- 如果确实有退化，这点退化是不是能接受

### 9.2 为什么最终没有保留 `all_2x`

`all_2x` 的问题，不是它没有提升，而是它的提升方式太平均了。

它让所有地方都一起吃成本，但不是所有地方都同样值这个成本。对于一些视觉收益更有限的元素来说，这种统一抬高更像是一种“顺手也一起变贵”的处理，而不是一种有明确投资回报的选择。

换句话说，`all_2x` 更像一种很整齐的方案，但不一定是当前案例里最划算的方案。浏览器实测给我的判断是：它确实比混合采样更好看一点，但没有好到足以覆盖它额外带来的整体时间成本。

### 9.3 为什么混合采样更合理

后面之所以收敛到 `Motorway + Primary = 2x`，其余保持 `1x`，核心原因其实很简单：主干道更接近用户会真正注意到的视觉重点。

如果有一部分高倍率预算必须保留，那它更应该优先给这些最显眼、最影响整体观感层次的元素，而不是无差别地平铺到所有元素上。

这不是一个“算法上更优雅”的选择，而是一个“预算分配更合理”的选择。

### 9.4 这一步本质上不是选参数，而是在做取舍决策

这也是为什么我一直不想把这轮优化写成“最后选了哪个配置”的简单故事。

真正发生的事情不是：

- 我找到了一个神奇参数

而是：

- 我在几个候选方案之间，按照体感收益、视觉损失和总成本，画出了一条当前可接受的边界

这条边界背后的原则后来也越来越清晰：

> 如果一个方案只能换来大约 10% 左右的总时长改善，但要付出明显可感知的画质代价，那这个取舍对当前场景来说就不值得。

这句话其实决定了很多候选方向为什么最后没有继续推进。不是因为它们完全没效果，而是因为它们的收益不足以抵消它们带来的损失。

如果把最后的判断压缩成一张更接近工程决策的表，它大致会是这样：

| 方案                                  | 渲染总耗时 | 视觉收益                         | 主要代价                               | 是否保留             |
| ------------------------------------- | ---------: | -------------------------------- | -------------------------------------- | -------------------- |
| `all_1x / export 1x`                  |  6461.9 ms | 成本最低，但主干道边缘退化最明显 | 关键视觉点损失较大                     | 作为低成本基线保留   |
| `all_2x / export 1x`                  | 13827.3 ms | 整体更整齐                       | 几乎所有阶段一起变贵，边际收益不成比例 | 不作为默认方案保留   |
| `Motorway + Primary = 2x / export 1x` | 10122.0 ms | 保住主干道最关键的收益           | 仍有明显成本，但低于 `all_2x`          | 作为最终混合采样保留 |

### 9.5 为什么这个结论值得强调

很多性能优化讨论最后都会退化成“哪个数字更好看”，但真实工程决策很少这么简单。

用户不会因为内部某个阶段省了几百毫秒就天然高兴；他们只会在最终等待时间明显缩短、而且结果质量没有明显变差时，真正感受到优化的价值。

所以这次最终保留混合采样，并不是一个妥协到中间值的无奈选择，而是一次相对明确的判断：在当前问题和当前约束下，它更接近**符合用户体感收益与质量约束的方案**。

## 结语

回头看，这次最有价值的收获，并不只是把导出时间从一组很糟糕的状态拉回到了一个更可接受的水平。

更重要的是，我最后得到的并不是一个孤立的“更快参数”，而是一套更清楚的判断：先把默认导出流程里不该存在的重分支拿掉，再用浏览器主基准去比较哪些采样成本真正值得保留，最后把更高倍率预算留给用户更容易看到差异的部分。

这也是为什么，最终留下来的不是一个统一更高倍率的方案，而是一套更克制的混合采样配置。它未必是普适答案，但至少在这次案例里，它比继续无差别抬高所有阶段的成本更合理。

如果一定把这篇文章压缩成一句话，那就是：**真正值钱的性能优化，往往不是把每一段代码都再抠快一点，而是先把默认流程纠正过来，再把成本花在真正值得保留质量的地方。**
